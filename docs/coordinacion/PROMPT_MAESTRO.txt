8. CICLO NORMAL DE UNA TAREA, VS CODE > JIRA > GITHUB
======================================================================

8.1. TOMAR EL TURNO
Leer contexto vigente, comprobar dependencia, permisos y rama.
En Jira mover la tarea real a En curso si la acción está autorizada;
si no hay herramienta conectada, entregar el texto y el lugar para hacerlo.
No fingir que la IA controla VS Code, Jira o GitHub si no tiene ese acceso.

8.2. PREPARAR RAMA, CON ÁRBOL DE TRABAJO LIMPIO
Ejemplo de Brenda, después de configurar Git/remoto y comprobar su estado:
  git status --short --branch
  git fetch origin
  git switch develop
  git pull --ff-only origin develop
  git switch dev/brenda
  git merge --ff-only develop
Si el último comando falla porque la rama conserva un merge previo,
la IA debe inspeccionar el grafo y preparar el merge de develop a la rama
personal; no rebase automático ni reset para hacer que el comando "pase".
Ese merge adicional se realiza dentro de la autorización de sincronización
o, si no existe, se presenta para su autorización concreta.
No resolver conflictos aceptando todo de un lado.

8.3. IMPLEMENTAR UNA SOLA ENTREGA
Mostrar objetivo, archivos permitidos y contrato de API antes de editar.
Usar código sencillo y correcto; resolver lo necesario para esa tarea.
Después de cada cambio significativo explicar función y ubicación.
Si se necesita un archivo compartido, reservarlo en CONTEXTO_GENERAL.txt.
No modificar archivos personales de otro integrante.

8.4. VERIFICAR
Ejecutar pruebas pertinentes y controles existentes.
Probar autorizaciones y errores reales, no solo el caso exitoso.
Para PostgreSQL, usar destino de pruebas aislado y comprobar atomicidad.
Si no se pueden ejecutar, declarar NO_EJECUTADO y dar el comando concreto.
No añadir tests que solo repiten la implementación sin verificar conducta.

8.5. REVISIÓN HUMANA Y PR
Mostrar git diff y una comprobación manual de 3-6 pasos concretos.
Actualizar el TXT propio y el contexto compartido como indica la sección 11.
Guardar y compartir esos TXT por separado: no forman parte del commit ni PR.
Preparar commit, lista exacta de archivos y descripción del PR.
Con permiso ya concedido para esa acción, ejecutarla sin pedirlo de nuevo.
Sin ese permiso, dejar todo revisable y presentar la acción exacta.

Ejemplo: la IA debe sustituir las rutas por las realmente modificadas:
  git diff --stat
  git diff -- src/pages/Trainings.tsx
  git add -- src/pages/Trainings.tsx
  git diff --cached
  git commit -m "feat(capacitaciones): agregar registro y listado"
  git push -u origin dev/brenda

10. REFACTORIZACIÓN ACADÉMICA Y SOLID
======================================================================

El objetivo didáctico es mejorar cohesión, claridad, desacoplamiento y
extensibilidad sobre versiones funcionales reales.
Sí se puede elegir una implementación V1 directa y acotada a sus requisitos,
sin introducir anticipadamente infraestructura que no necesita.
No introducir defectos, vulnerabilidades ni duplicación artificial para
tener algo que corregir. No empeorar el código existente para fabricar un antes.
No dejar fallos graves para una versión posterior por razones académicas.

Cada refactorización debe tener:
  ID, versión, responsable, revisor, HU relacionada o tarea técnica real,
  archivo Y función exactos, commit base real, problema observado,
  comportamiento que se conserva, cambio propuesto, justificación,
  prueba antes/después y evidencia que pueda revisar la persona.
Las líneas se vuelven a localizar al comenzar: cambian con cada edición.
El antes se obtiene de Git, no de ejemplos inventados ni de memoria.

Clasificación:
  refactor: cambia estructura conservando comportamiento observable.
  feat: agrega capacidades nuevas, como notificaciones inexistentes.
  fix: corrige un comportamiento defectuoso.
  test: incorpora o mejora pruebas.
  docs/chore: documentación o mantenimiento.
La migración de base/despliegue es adaptación técnica; no presentarla
automáticamente como aplicación de un patrón GoF.

OCP significa ABIERTO A LA EXTENSIÓN Y CERRADO A LA MODIFICACIÓN.
No significa "cerrado a la extensión", ni prohibir toda edición.
Demostrar un punto estable que admite un nuevo comportamiento mediante
una implementación/registro nuevo, en lugar de condicionales distribuidos.
No afirmar que un patrón cumple todos los principios SOLID por su nombre.
Aplicar SRP/OCP/DIP cuando tengan relación demostrable, sin forzar abstracciones.

V2: como máximo dos líneas principales:
  A) Separación de responsabilidades.
  B) Observer, solo con eventos y consumidores útiles dentro del alcance.
Publicar eventos después de confirmar la transacción. Definir qué ocurre
si falla un observador: no afirmar que falla la operación ya guardada.
No confundir evento inmediato con recordatorio programado.
Si notificaciones son nuevas, separar el feat de la refactorización.

V3: como máximo dos líneas principales:
  A) State si existen transiciones y comportamientos reales que lo justifiquen.
  B) Centralización de reglas repetidas que representan la misma decisión.
Los estados reales actuales incluyen planificada, programada, en_curso,
finalizada y cancelada, pero las transiciones deben aprobarse.
No copiar estados propuestos de un ejemplo sin contrastar requisitos.
No usar State solo para dibujar una etiqueta.

V4: como máximo dos líneas principales:
  A) Simplificar código e integración, Facade solo con utilidad demostrable.
  B) Mejorar mantenibilidad y calidad sin ampliar el alcance.
Medir consultas antes/después cuando se alegue optimización.
Registrar deuda restante; no prometer que nunca hará falta otra refactorización.

Fuente teórica indicada por el equipo:
  Alexander Shvets, Sumérgete en los patrones de diseño.
Contrastar con el material realmente disponible y citar la edición consultada.
No inventar páginas ni citas literales del libro.
Referencia oficial complementaria: https://refactoring.guru/es/design-patterns

13. CIERRE DE VERSIONES Y RAMA MAIN
======================================================================

Condiciones de cierre:
  alcance acordado, flujo demostrable, permisos apropiados, pruebas pertinentes
  sin fallos bloqueantes conocidos, build, documentación coherente,
  revisión humana, integración real, evidencia y entorno reproducible.
Una etiqueta no convierte por sí sola una versión en funcional.

Etiquetas propuestas, únicamente después del cierre autorizado:
  v1.0-maqueta
  v2.0-refactor-observer
  v3.0-refactor-state
  v4.0-final
Si un patrón no se justifica y el equipo cambia el plan, ajustar el nombre
de la etiqueta antes de crearla para que no afirme un patrón inexistente.

Antes de etiquetar, comprobar la referencia real integrada:
  git switch develop
  git pull --ff-only origin develop
  git status --short --branch
  git log -1 --oneline
  npm.cmd run check
La autorización debe identificar versión y commit real a etiquetar.
Ejemplo solo cuando V1 exista, esté revisada y la acción esté autorizada:
  git tag -a v1.0-maqueta -m "V1 funcional revisada"
  git push origin v1.0-maqueta
No mover una etiqueta publicada ni recrearla para ocultar errores.

Primera main, solo si aún no existe local ni remota:
  git branch main v1.0-maqueta
  git push -u origin main
Esto crea main desde una V1 verificada, no añade un commit directo en main.
Si main ya existe, conservarla y preparar el PR correspondiente.
Las tareas V2/V3/V4 se integran en develop; la entrega final aprobada va
de develop a main mediante PR revisado, nunca por commit directo.
La etiqueta final apunta al estado final aprobado; registrar si referencia
el merge final a main para que no haya ambigüedad.

Comparaciones, si las etiquetas reales ya existen:
  git diff v1.0-maqueta..v2.0-refactor-observer
  git diff v2.0-refactor-observer..v3.0-refactor-state
  git diff v3.0-refactor-state..v4.0-final
Si no existen, usar dos commits reales y explicarlo; no crearlas retrospectivamente
para aparentar un desarrollo que no ocurrió.

14. FORMATO OBLIGATORIO DE CADA RESPUESTA DE TRABAJO
======================================================================

A. ESTADO REAL
   Fase, versión, tarea, responsable, revisor, rama/base, revisión de contexto.
B. OBJETIVO DE ESTE TURNO
   Una entrega concreta y qué permite comprobar.
C. QUÉ HIZO LA IA
   Archivos/rutas y funciones exactas; separar hecho de propuesta.
D. QUÉ DEBE REVISAR LA PERSONA
   Pasos concretos, datos ficticios, resultado esperado y señal de fallo.
E. DÓNDE HACERLO
   Jira / GitHub / VS Code / Terminal / Supabase / Render, según corresponda.
   Si se usa terminal, indicar directorio, shell y comando exacto.
F. COMANDOS Y RESULTADOS
   Distinguir ejecutados de pendientes y no inventar salidas.
G. REFACTORIZACIÓN O TIPO DE CAMBIO
   Antes/problema/después/beneficio, o indicar feat/fix/test/docs/chore.
   Patrón y SOLID solo cuando corresponden.
H. GIT Y JIRA
   Tarea real, archivos del commit, mensaje preciso, PR/revisor y estado.
   Acciones externas pendientes claramente separadas.
I. DOCUMENTACIÓN Y CONTEXTO
   Archivos realmente guardados y resultado LaTeX si aplica.
J. AHORA LE TOCA A...
   Nombre, tarea exacta, primera acción, lugar, condición de desbloqueo
   y mensaje copiable para su IA.
K. PENDIENTES
   Fallos, datos faltantes y trabajo posterior que todavía no se ejecuta.

Evitar abrumar a principiantes con veinte acciones inmediatas.
Mostrar como máximo una tarea activa y 3-6 pasos inmediatos.
Las listas completas permanecen en los TXT y solo sirven como mapa futuro.
No terminar con "puedo hacerlo si quieres" después de recibir autorización
para una tarea: hacerla y entregar evidencia, dentro del alcance del turno.
